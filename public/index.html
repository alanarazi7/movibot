How it works

One ReAct loop: reason → act → observe → stop?, for at most five model turns. Every tool is on the table on every turn. The planner chooses which to call, with what arguments, how many at once, and when it has enough to answer. Exactly one step costs money — the planner. Three of the four tools are free, and the fourth costs two millionths of a dollar.

The cheapest-first ordering is a preference, not a path. Nothing in agent/loop.py sequences the tools; the order is policy, argued for in the system prompt, and the planner departs from it whenever a request calls for something else. When it does follow the order, each call hands the next a smaller candidate set, so the token-heavy tool only ever sees what survived the free ones. A question answerable by filtering alone costs two model turns and never touches the other three. The candidate set lives in Python between calls and never enters the prompt.

🔁 Why this is an agent, not a pipeline

A fair thing to ask of the diagram above: four tools, a recommended order, a set that shrinks at each step — is this an agent, or a pipeline with a language model bolted to the front?

The distinction is policy versus mechanism. A pipeline's order is in its code. MoviBot's is in its prompt. All four tool schemas are offered on every non-final turn (agent/loop.py), the model picks freely among them, and the loop ends when it emits no tool call at all. Nowhere does the code say “filter, then screen, then search, then read.”

Which makes the claim testable, because it predicts something a pipeline cannot do: the trace should change shape with the request. Two verified tool paths from /api/agent_info, same agent, same code:

RequestTraceTools used
“Best empowering princess movie besides Frozen and Moana” Planner → CatalogFilter → Planner → answer 1 of 4
“Something safe for a toddler where nobody dies” Planner → CatalogFilter → LexicalScreen → Planner → answer 2 of 4

Three of the four tools never ran in the first case. A pipeline runs its stages; an agent skips what the request does not need, and here it decided that for itself from the conditions it had written out one turn earlier.

Three further things the loop affords that a fixed sequence does not. The planner is instructed to re-query after observing — a search that comes back unconvincing gets re-phrased as a different concrete event and run again, which is a decision taken from a result rather than from the plan. A single turn may carry several tool calls, so independent conditions need not be serialised. And the agent stops on its own judgement: MAX_ROUNDS is a spending cap, reached only when something has gone wrong, not the normal way a request ends.

What is genuinely fixed is smaller than it looks, and deliberately so: the 45-minute runtime floor, the rating adjustment, and the working-set scoping are invariants in Python that no plan can route around. Those are not stages. They are the things an agent is not allowed to decide.

🧭 How a request flows

Before its first tool call, the planner decomposes the request into conditions and types each one. This is free: it rides along in the same message that makes the first call, rather than costing a turn of its own. A dedicated planning step would have doubled the paid turns of every request to produce the same text.

The types matter because each kind of condition is settled by exactly one tool, and a condition is not satisfied until its own tool has settled it. That is a rule about evidence, not about order: it says which tool can close a given condition, never which condition to take up first, or how many turns to spend, or whether to go back. Those stay with the planner.

Condition kindExampleSettled by
structured“a Pixar film”, “in French”, and negatives the catalog stores — “not Pixar”, “no musicals”, “besides Frozen”filter_catalog
lexical — absence“nobody dies”, “nothing scary”screen_out keep='clear'
lexical — presence“an animal that wears a hat”, “a film with a train”screen_out keep='flagged'
semantic“a rat who wants to cook”search_plots
narrative“who betrays whom”, “is the ending sad”read_synopses

Why a lexical condition is scanned, not searched

This is the one counter-intuitive piece. Embed “nobody dies” and the top results are the films where somebody does — because that is what the text of those films says. Similarity finds the films that fail the condition.

So this kind of negation is screened instead: every plot passage of every candidate is scanned for a word list. Two properties make this the right tool rather than a shortcut. No film escapes the check by ranking eleventh, which top-k retrieval can never promise. And its error is one-sided: “dead heat” over-excludes, it never under-excludes, which for a negative request is the harmless direction.

The same scan runs forwards. A concrete presence fails ranking for a different reason: “an animal that wears a hat” is one small detail inside a 300-token passage, and similarity scores the whole passage — so you get films about animals whose plots never mention a hat, while the film whose plot says the hat “lands on Tod” places nowhere. Scanning for the word finds it: keep=’flagged’ returns every film in scope whose plot text uses one, each with the passage that matched, because a word list cannot tell you that Bowler Hat Guy is a man and Judy Hopps is a rabbit. And when the scan comes back empty, that is the answer: plot text records what happens rather than what things look like, so the agent reports the gap in its sources instead of naming films it could not verify.

What a screen proves, and what it does not. It is exhaustive over its word list, not over the event. A clear result means no listed word appears in the film's stored plot text — which an event can evade by being narrated in other words, or by not being written down at all. So the agent is required to report it as what it is (“no death-related terms appear in its plot text”) rather than upgrading it to “nobody dies”, and to read the synopsis when the stronger claim is what the request actually needs.

Screening is where a negation starts, not where it must end. Negations the catalog stores — “not Pixar”, “no musicals” — never reach the screen at all; they are column lookups. And negations that are concepts rather than vocabularies — “not depressing”, “doesn't focus on romance” — cannot be settled by any word list, so they escalate to search and reading instead, with whatever uncertainty remains stated in the answer.

What it cannot do is tell an attempt from an outcome. “Randall attempts to kill Sulley”, “believing Woody murdered Buzz” — nobody dies in either. That is modality, not vocabulary, and no word list resolves it. So a match makes a film flagged, meaning unresolved, never rejected, and the matching quote comes back with the flag so the planner judges two sentences instead of a 5,000-word plot.

Answer: Inside Out (7.83), WALL·E (7.73), Toy Story 3 (7.52). Ten films were flagged and none had insufficient text. Two model turns, no embedding, no synopsis read. Ranking-then-verifying would have spent a search plus up to eight synopsis reads to reach somewhere less certain.

Note the turn column. Two conditions were settled in one call, because the planner recognised they belonged to the same tool and packed them together; the fourth needed no tool at all, and it worked that out rather than spending a turn to discover it. Then it stopped — with PlotSearch and SynopsisReader still available and three turns of budget unspent.

What the answer may claim

Two tools are exhaustive and two are not, and the difference decides what the agent is entitled to say. filter_catalog and screen_out check every candidate, so their findings are complete: 76 films clear on the death screen means all of them, not a sample. search_plots returns a top handful and read_synopses is capped at eight films, so anything resting on those is the best among those examined — and the prompt requires saying which is meant.

The screen returns three buckets for the same reason. clear is a finding. flagged is unresolved. insufficient_text means the film had too little plot text to screen at all, so it was verified neither way — that bucket exists because 13 films would otherwise pass a death screen simply by having nothing to scan, and absence of evidence would get reported as evidence.

🔒 Guardrails, and where they live

The invariants are enforced in the data and the tool code, never in the prompt. A prompt is the wrong place for a rule that must not be forgotten: the 45-minute feature floor is applied at data preparation time, and results are ordered by a vote-count-adjusted rating inside the tools, so no plan can bypass either. The prompt is not even told about them.

The one that matters most for the screen is MIN_SCREEN_TOKENS. A film is only certified clear if it offered enough plot text for the absence of a match to mean something — median plot length is 1,207 tokens for clear films against 2,153 for flagged ones, precisely because a short summary has fewer chances to contain any given word. Without that floor, the thinnest entries in the catalog would look like the safest.

Data

🧰 How this catalog was built

Three sources go in. A Kaggle catalog supplies the structure — ids, dates, runtime, genres, studios, votes, keywords — and is the only one that supports deterministic filtering. Its descriptions are too thin to reason about, so MPST plot synopses supply the real story text. Wikipedia supplies independent verification text, scraped once offline: the Plot section for scene questions, and everything else — cast, production, reception — for tone questions the plot cannot settle.

Why only Disney and Pixar

It keeps the catalog in family territory and makes the demo coherent, but the real reason is a constraint: the assignment caps stored data at 50 MB and the full catalog does not fit. For a real product, scaling this to all movies would be straightforward — this is a proof of concept, not a ceiling.

Why nothing after 2017

The Kaggle dataset is a snapshot published in 2017, so its metadata simply stops there. This is a property of the source, not a filter we chose: the newest films in the catalog are Cars 3, Beauty and the Beast, and Guardians of the Galaxy Vol. 2, all 2017, and 21 films date from 2015 or later. Anything since — Frozen II, Encanto, Turning Red — does not exist as far as this system is concerned. The agent is told this explicitly and refuses questions about recent or current releases rather than answering them from a stale catalog. Again, fresher data is perfectly obtainable — this snapshot was simply the convenient choice for a proof of concept.

Duration filter

Disney and Pixar both release short films alongside features, and a six-minute short is never what someone asking for “a movie” wants. Anything under 45 minutes is dropped, which removes 65 titles; one further row went for a non-positive runtime.

Ranking

Unless the request says otherwise, the agent aims to return the best-ranked films. Raw rating alone cannot express that, because a film with very few votes can carry a very high score. Each film therefore carries a weighted_rating — the formula IMDb uses for its Top 250 — which pulls thinly-voted films toward the catalog average until they earn enough votes to stand on their own: 

weighted_rating = (v / (v + m)) × R  +  (m / (v + m)) × C

R = the film's rating     v = its vote count
C = 6.199 catalog mean    m = 300 vote prior

It ranks rather than filters, so nothing is removed and no answer becomes unreachable — thinly-voted films are demoted on broad queries and still win narrow ones where they are the right answer. Sort the table by Best rated to see the result.

Worth being honest about: “best” is ill-defined here. This is an adjusted average of public votes — a proxy for broad approval, not a measure of quality, and it knows nothing about the person asking. It is a reasonable default when the request gives no other basis to sort on, not a claim about which films are actually better.

📐 How retrieval was built

Four corpora, chunked into passages, embedded by one model, scored with a dot product. Each corpus answers a different kind of question, which is why they stay separable: a plot says whether someone dies, a reception section says whether a film is thought frightening.

CorpusFilmsPassagesWhat it answers
Plot synopses (MPST)1591,254What happens, in full
Wikipedia plot233826The same, for the 75 films MPST misses
Wikipedia context237841Cast, production, reception, tone
Catalog overview238238Thin, but exists for every film
All four2383,159Every film is now searchable

Why passages, not whole films

The embedding model accepts 8,191 tokens and the median synopsis is 1,143, so a whole film would fit in one vector. It still shouldn't. One vector for a 28,000-character story averages thirty unrelated beats together: Frozen's betrayal sits 81% of the way through and could never outrank the film's own opening. Splitting also gives the agent something to quote — a passage is evidence, a document-level vector is not.

Sentences, not paragraphs

The obvious approach is to accumulate paragraphs to a token budget, which is what our earlier RAG project did. Measured here it produces nothing: zero of the 159 synopses contain blank-line paragraphs and 66 have no newline at all, so a paragraph splitter would emit one chunk per film. Passages are built from sentences instead.

The parameters, against the course guidance

ParameterOursCourse defaultWhy we differ
Chunk size300512–1024The retrieval unit is a story beat, not a section. At 23 tokens per sentence, 300 holds about one scene.
Overlap20%5–15%A beat split across a boundary must survive whole somewhere; a half-quoted betrayal is not usable evidence.
Min passage50—Not a discard threshold. A shorter tail is merged into the previous passage, so no sentence is ever lost.

One embedding model, everywhere

text-embedding-3-small, 1536-dim, for both indexing and queries. An earlier design ran a local model in development and this one in production, which meant local testing never exercised the rankings production would return. Passages are embedded once and cached by content, so re-running only pays for what changed.

No vector database

The vectors live in memory, in a committed file scored with numpy. There is no vector database and no switch to enable one, which is a decision rather than a shortcut: 3,159 vectors is not a search problem. Scanning all of them takes about 0.5 ms, against 50–200 ms for a round trip to a hosted index — and the query has to be embedded through the API either way, so a database saves nothing there.

What it would add is a credential, an account, a quota, another failure mode, and a fresh clone that cannot retrieve until someone provisions an index. Shipping the matrix with the code also means a given commit retrieves identically forever. A vector database earns its place when the index stops fitting in memory or brute force stops being instant; at 19 MB, neither is close.

What still doesn't work

Retrieval is sensitive to phrasing. Asked for “a prince reveals he never loved her and leaves her to die”, Frozen ranks #2. Asked the same thing abstractly — “someone you just met turns out to be the villain” — it falls outside the top 25. Moving to a stronger embedding model did not fix this. The agent is therefore instructed to search for concrete events rather than themes, which is a workaround, not a solution.

Rebuilding it

Ingest is a local job: it writes the index into the repo, and a serverless filesystem is read-only. Passages are cached by content, so re-running only pays for what changed. 

python -m rag.ingest --dry-run --sources all   # free
python -m rag.ingest --debug   --sources all   # ~$0.0002
